# Карта файлов Android ROM

Этот документ простыми словами объясняет, из каких частей обычно состоит Android ROM или исходное дерево Android. Он нужен для AelitaOS на Xiaomi 11 Lite 5G NE (`lisa`), чтобы перед изменениями понимать, какая папка за что отвечает.

AelitaOS пока не является собираемой или прошиваемой прошивкой. На этом этапе мы только изучаем структуру и готовим безопасную стратегию выбора базы.

## `device/` — конфигурация конкретного устройства

Папка `device/` описывает, как Android должен собираться и запускаться на конкретном телефоне. Для `lisa` здесь в будущем должны быть настройки именно Xiaomi 11 Lite 5G NE, а не похожего устройства.

Обычно внутри бывают:

- `BoardConfig.mk` — низкоуровневые параметры платы: архитектура, размеры разделов, формат загрузочных образов, путь к kernel/dtb/dtbo, параметры recovery и vendor_boot. Ошибка здесь может привести к неработающей сборке или не загружающемуся телефону.
- `device.mk` — список пакетов, файлов, конфигураций и свойств, которые нужны устройству. Через него подключают HAL, overlays, permissions XML, init-файлы и другие части устройства.
- `AndroidProducts.mk` — объявляет продукты, которые можно выбрать для сборки. Он связывает product makefile с именем продукта.
- Product makefiles — файлы продукта, например будущий `aelita_lisa.mk`. Они описывают, что именно собирается как AelitaOS для `lisa`: базовый Android, устройство, приложения, overlays и брендирование.
- Init files (`init*.rc`) — сценарии раннего запуска Android: какие сервисы стартуют, какие права выставляются, какие каталоги создаются. Их нельзя менять наугад, потому что ошибка может остановить загрузку.
- `fstab` — таблица разделов и точек монтирования. Она говорит Android, где находятся `system`, `vendor`, `product`, `data`, `metadata` и другие разделы, а также как включается шифрование и проверка целостности.
- Overlays — ресурсные переопределения. Через них меняют значения по умолчанию, поведение интерфейса, брендинг, настройки лаунчера и системные ресурсы без переписывания framework.
- `sepolicy` — правила SELinux для устройства. Они определяют, какие процессы к каким файлам, сокетам и сервисам могут обращаться.
- Recovery settings — параметры recovery: какой экран, какие разделы обновлять, как устроен установщик, какие особенности у устройства. Неверные настройки recovery могут помешать обновлению или восстановлению.

## `vendor/` — проприетарные компоненты и настройки производителя

`vendor/` содержит закрытые компоненты, которые нужны железу: камеры, модему, графике, датчикам, аудио, Wi-Fi, Bluetooth и другим частям телефона.

Важно: vendor-часть нельзя собирать из случайных файлов. Нужно понимать источник, лицензию, совместимость с firmware и Android-версией.

Обычно встречаются:

- Vendor blobs — готовые бинарные библиотеки и сервисы производителя. Они нужны для работы железа, но их нельзя править как обычный исходный код.
- Firmware dependencies — зависимости от конкретной версии firmware, modem, DSP, Bluetooth/Wi-Fi firmware и других низкоуровневых частей. Несовпадение может сломать связь, камеру, звук или загрузку.
- `proprietary-files.txt` — список файлов, которые нужно извлечь из стоковой прошивки или устройства.
- `extract-files.sh` и похожие скрипты — инструменты для извлечения blob-файлов из подключенного телефона или распакованного стокового пакета. В этом PR такие скрипты не добавляются.
- Vendor makefiles — makefile-файлы, которые подключают извлеченные blobs и vendor-конфигурацию в сборку.

Почему нельзя коммитить случайные blobs без ревью:

- можно смешать файлы от другого устройства;
- можно нарушить лицензии;
- можно получить несовместимость с kernel или firmware;
- можно добавить лишний закрытый код, который невозможно проверить;
- можно сделать сборку нестабильной или опасной для прошивки.

## `kernel/` — ядро Linux или стратегия ядра

Android использует Linux kernel. Для ROM важно либо иметь исходники ядра, либо четко понимать, какое готовое ядро используется и откуда оно берется.

Основные элементы:

- Kernel source — исходный код ядра для устройства или семейства устройств. Лучший путь — использовать проверенный исходник, совместимый с `lisa`.
- `defconfig` — базовая конфигурация сборки ядра: включенные драйверы, модули, безопасность, файловые системы, параметры платформы.
- DTB/DTBO relation — device tree описывает железо для ядра: дисплей, тач, память, камеры, GPIO, питание и другие узлы. DTB обычно содержит базовое описание, DTBO — overlay-изменения.
- `vendor_boot` relation — на современных Android часть device-specific ramdisk находится в `vendor_boot.img`. Kernel, vendor ramdisk и device tree должны совпадать по ожиданиям.

Почему несовпадение ядра опасно:

- телефон может не загрузиться;
- могут не работать камера, связь, звук, датчики или тач;
- может сломаться шифрование данных;
- может появиться bootloop;
- могут нарушиться SELinux и init-сервисы.

## `system/` — базовая Android-система

`system/` — это основная часть Android: framework, системные приложения, базовые сервисы и общие конфигурации.

Сюда относятся:

- Framework — Java/Kotlin/C++-слой Android, системные API, службы, ресурсы и логика платформы.
- System apps — приложения, поставляемые вместе с системой. Они могут быть обычными системными приложениями или privileged-приложениями.
- Permissions XML — XML-файлы, которые объявляют системные возможности, shared libraries, features и разрешения для приложений.
- `priv-app` vs `app` — `app` означает обычное системное приложение без автоматических privileged-разрешений. `priv-app` может получать специальные разрешения только при наличии правильных allowlist XML и политики. Ошибка здесь может создать дыру в безопасности или сломать загрузку.

Aelita-Fon в будущем может жить в `system`, `product` или `vendor` в зависимости от выбранной базовой ROM-структуры. На раннем этапе безопаснее думать о нем как о preloaded/system app, а не как о глубоко привилегированном компоненте.

## `product/` — продуктовые приложения и настройки

`product/` хранит то, что относится к конкретному продукту или варианту ROM, а не к общему Android и не к железу.

Обычно здесь бывают:

- Product packages — приложения и пакеты, которые входят именно в этот продукт.
- Product overlays — переопределения ресурсов для брендинга, стандартных настроек и поведения.
- Брендинг AelitaOS — в некоторых деревьях это хорошее место для названия, обоев, настроек лаунчера и предустановленного Aelita-Fon.

## `system_ext/` — расширенный системный слой

`system_ext/` появился как дополнительный слой между общей системой и продуктом/OEM-частями. Производители и ROM-разработчики могут размещать здесь компоненты, которые расширяют платформу, но не являются чистым AOSP `system`.

Примеры: OEM platform apps, расширения framework, дополнительные permissions XML и системные сервисы, если так устроена выбранная ROM-база.

## `odm/` — OEM/device hardware configuration

`odm/` обычно содержит настройки производителя устройства, связанные с железом. Это может быть конфигурация HAL, аудио, камеры, датчиков или другие device/OEM-specific файлы.

Разница с `vendor/` зависит от конкретной архитектуры прошивки. В простом понимании: `vendor/` — общий vendor-слой, `odm/` — более конкретные настройки модели/производителя устройства.

## `boot.img` — ранняя загрузка

`boot.img` обычно содержит:

- kernel;
- ramdisk;
- ранний init;
- базовую логику старта Android.

Если `boot.img` не соответствует устройству, kernel, Android-версии или разделам, телефон может уйти в bootloop или не загрузиться.

## `vendor_boot.img` — vendor ramdisk для современных Android

На современных Android часть ramdisk вынесена в `vendor_boot.img`. Там могут быть device-specific init-файлы, модули и ранние компоненты, нужные железу.

`vendor_boot.img` должен быть согласован с kernel, vendor, dtb/dtbo и device tree. Смешивать его от разных баз опасно.

## `dtbo.img` — device tree overlays

`dtbo.img` содержит device tree overlays: описания и изменения аппаратной конфигурации для ядра. Они помогают kernel понять конкретные варианты железа.

Неверный `dtbo.img` может сломать дисплей, тач, камеры, питание, датчики или саму загрузку.

## `vbmeta.img` — Android Verified Boot metadata

`vbmeta.img` относится к Android Verified Boot. Он содержит метаданные проверки разделов и цепочку доверия.

Если `vbmeta` не соответствует остальным образам или ожиданиям загрузчика, загрузка может быть заблокирована. В этом документе нет команд прошивки: это только объяснение роли файла.

## `recovery.img` / boot recovery — среда восстановления

Recovery — отдельная среда для установки обновлений, сброса, диагностики и восстановления. На некоторых устройствах recovery может быть отдельным образом, на других — частью boot/vendor_boot схемы.

Для AelitaOS recovery важно только после выбора базы и проверки rollback-плана.

## `super.img` и dynamic partitions

Современные устройства часто используют dynamic partitions. Вместо отдельных физических разделов для `system`, `vendor`, `product` и `system_ext` есть большой контейнер `super`, внутри которого лежат логические разделы.

Зачем это нужно:

- гибко менять размеры разделов;
- поддерживать A/B обновления;
- проще обновлять набор системных разделов;
- уменьшить жесткую привязку к фиксированной разметке.

Для ROM это значит, что нельзя делать предположения о разделах без проверки layout конкретной базы и устройства.

## `sepolicy` — SELinux-правила

SELinux ограничивает доступ процессов к файлам, устройствам, сервисам и системным ресурсам. Это один из главных уровней безопасности Android.

Если Aelita-Fon позже станет privileged-приложением или системным сервисом, правила SELinux нужно добавлять осторожно:

- не выдавать широкий доступ без причины;
- понимать каждое разрешение;
- проверять логи denial;
- не отключать SELinux ради удобства;
- не маскировать реальные ошибки политики.

## Overlays — изменение ресурсов и дефолтов

Overlays позволяют менять ресурсы без прямого изменения исходников framework или приложений.

Через overlays можно менять:

- значения по умолчанию;
- брендинг;
- поведение лаунчера;
- feature flags;
- строки и ресурсы;
- некоторые системные настройки.

Это безопаснее, чем переписывать платформенный код, но каждое изменение все равно нужно проверять.

## `init*.rc` — стартовые сценарии Android

`init*.rc` описывают, какие сервисы запускаются во время загрузки, какие свойства выставляются, какие каталоги создаются и какие права назначаются.

Это опасная зона для случайных правок. Неправильный сервис, путь, пользователь, группа или SELinux context может вызвать bootloop или поломку hardware-сервисов.

## Manifests — список репозиториев исходного дерева

В Android source tree часто используется `repo`. Manifest-файлы описывают, какие Git-репозитории нужно скачать: Android source, device tree, vendor tree, kernel tree и дополнительные проекты.

`local_manifests` часто применяются для добавления device/vendor/kernel репозиториев поверх основной ROM-базы.

Для AelitaOS manifest должен фиксировать понятную, проверенную комбинацию исходников. Пока такой manifest не выбран.

## Lunch target / product name

Lunch target — это имя сборочной цели Android, например будущий вариант вроде `aelita_lisa-userdebug`.

Product name — имя продукта внутри makefile, например будущий `aelita_lisa`.

Сейчас это только будущая цель. AelitaOS для `lisa` еще не buildable, потому что не выбраны base ROM/source tree, device tree, vendor и kernel strategy.
