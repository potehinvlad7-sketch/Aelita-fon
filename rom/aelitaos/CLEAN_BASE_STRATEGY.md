# AelitaOS Clean Base Strategy

Главная идея: взять самую простую чистую рабочую ROM-базу для Xiaomi 11 Lite 5G NE (`lisa`) и постепенно превращать ее в AelitaOS.

На этом этапе AelitaOS не является прошиваемой сборкой. База еще не выбрана. Этот документ задает безопасный порядок мышления: сначала рабочая чистая основа, потом маленькие проверяемые изменения.

## Что значит clean base

Clean base — это база, у которой понятны:

- исходники или официальный источник;
- поддержка именно `lisa`;
- Android-версия;
- firmware requirement;
- recovery requirement;
- known bugs;
- способ отката;
- границы между device/vendor/kernel/system;
- возможность повторить сборку или хотя бы проверить происхождение образов.

Clean base не означает «любой ZIP из интернета, который кто-то назвал рабочим». Для AelitaOS нельзя начинать с непроверенной смеси vendor/kernel/boot от разных устройств.

## A. AOSP / LineageOS-like source base

Это самый чистый долгосрочный путь.

Плюсы:

- лучше подходит для no-Google и Aelita-first направления;
- проще понимать, какие компоненты входят в систему;
- легче добавлять Aelita-Fon как системный компонент постепенно;
- лучше для аудита, повторяемости и контроля;
- меньше зависимости от закрытых OEM-надстроек.

Минусы:

- нужен build host;
- нужны проверенные `lisa` device tree, vendor и kernel strategy;
- нужно проверить, что база реально загружается на устройстве;
- больше работы до первого результата.

Вывод: это предпочтительный долгосрочный путь AelitaOS, если найдены надежные исходники и понятная поддержка `lisa`.

## B. Existing clean custom ROM for lisa

Это быстрый путь для проверки реальной загрузки устройства и понимания практических требований `lisa`.

Плюсы:

- быстрее получить опыт с реальной прошивкой;
- можно увидеть требования к firmware/recovery;
- можно изучить known bugs и структуру работающей сборки;
- может быть полезным reference для будущей source-based работы.

Минусы:

- нельзя слепо копировать чужую сборку;
- источник, maintainer и device codename нужно проверять;
- могут быть скрытые изменения, GApps, проприетарные добавки или непонятный kernel;
- не каждая готовая ROM подходит как база для AelitaOS.

Что обязательно проверить:

- точный codename `lisa`;
- source URL;
- maintainer/source trust;
- Android version;
- firmware requirement;
- recovery requirement;
- installation method;
- known bugs;
- rollback method.

Вывод: можно использовать как reference и для обучения, но не как источник для слепого копирования.

## C. GSI

GSI полезен для быстрого Treble-эксперимента.

Плюсы:

- быстрый способ проверить общую совместимость Project Treble;
- можно быстро увидеть, как generic system ведет себя на устройстве;
- полезно для обучения разнице между generic system и device-specific слоями.

Минусы:

- слабее hardware-specific integration;
- могут быть проблемы с камерой, датчиками, VoLTE, fingerprint, brightness, audio и другими функциями;
- не дает полноценной `lisa` ROM-архитектуры;
- не идеален как финальная база AelitaOS.

Вывод: GSI можно рассматривать только как эксперимент, не как целевую основу AelitaOS.

## D. Stock HyperOS-based modification

Это путь с лучшей совместимостью железа, потому что он ближе всего к заводской прошивке.

Плюсы:

- максимальная hardware compatibility;
- меньше риска потерять камеру, модем, датчики и OEM-функции;
- проще сравнивать с текущим состоянием телефона.

Минусы:

- сложнее сделать clean/no-Google систему;
- больше закрытых компонентов;
- сложнее аудит;
- сложнее убрать OEM/Google-зависимости без поломок;
- можно застрять в модификации стока вместо создания AelitaOS.

Вывод: не первый выбор. Имеет смысл только если чистый source-based путь не удается подтвердить.

## Verdict

Предпочтительная стратегия AelitaOS:

1. Изучить карту файлов Android ROM.
2. Выбрать чистую `lisa`-совместимую базу или source tree.
3. Проверить rollback до любых flash-экспериментов.
4. Сначала собрать или прошить чистую базу без Aelita-изменений.
5. Добавить Aelita-Fon как preloaded/system app.
6. Только после этого добавлять более глубокую интеграцию AelitaOS.

## Практическое правило

Каждый шаг должен быть обратимым и проверяемым. Если нельзя объяснить, откуда взят boot/vendor/kernel/system компонент и почему он подходит именно для `lisa`, этот компонент нельзя использовать как основу AelitaOS.
